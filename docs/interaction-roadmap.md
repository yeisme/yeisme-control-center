## 路线

### S1 全屏媒体查看器与可访问性基线（已完成，`yeisme-control-center-media-viewer-v1`）

一次点击打开；←/→、滑动切换；图片缩放平移；视频、文本；下载与查看详情；Esc 分层；焦点回到打开者。13 页 axe serious/critical 清零。

### S2 键盘与焦点（已完成，`yeisme-control-center-keyboard-focus-v1`）

- 任务、资源（表格与大图网格）、请求、提醒列表：↑/↓ 移动，网格里 ←/→ 横向移动，Home/End 到首尾，Enter 打开详情；页面搜索框里按 ↓ 进入列表。
- 关闭详情后焦点回到原行：打开者还在当前这一项里就回到打开者，否则回到这一项的行按钮；用鼠标点行里文字打开的也一样。
- 宽屏（≥1280）详情停靠在右侧，焦点留在列表，Tab 就能到行内的预览；窄屏详情是模态抽屉，焦点进入抽屉，关闭后回到行。原来宽屏第一帧会按模态渲染，把焦点抢进详情并锁住页面滚动，已改为同步读取屏宽。
- `/` 聚焦当前页搜索框（没有就打开命令面板），`?` 打开快捷键表，输入时和有弹窗时都不触发；快捷键表与实际行为共用 `src/shared/keyboard.ts`。
- 命令面板：空输入时先列“最近打开”（按身份与范围隔离，只存本标签页，退出登录清空），再列“操作”（切换主题、跟随系统、切换到其他范围、查看快捷键）。
- 顺带修复：“跳到主要内容”在 hash 路由下会把地址改成 `#main`，页面跳走；现在只移动焦点。
- 验收：浏览器旅程只用键盘完成“`/` 搜索 → ↓ → Enter → Tab 到预览 → Enter → Esc → Esc → 焦点回到原行”。

### S3 连续浏览（已完成，`yeisme-control-center-continuous-browsing-v1`）

- 播放队列：从资源库、任务中心、项目结果或任务详情的结果列表点播放，播放器带上该列表里可播放的音频（按当前筛选顺序）；浮动播放器有“上一条/下一条”和“2 / 6”，系统媒体键的上一首/下一首也接到队列。
- “播完自动播放下一条”在播放器“更多”菜单里，默认关闭、记在本机；关闭时一条播完就停，不会为下一条申请句柄。共享项目成果要先读任务才能播放，暂不进队列。
- 查看器缩略条：当前视图的结果排在底部，只用 owner 提供且允许预览的缩略图（懒加载、会话缓存），其余显示类型标记；只占一个 Tab 位，←/→ 仍然切换。
- 并排对比：图片上点“并排对比”，当前这张固定在左边（A，沿用已加载的图，不重新申请句柄），右边（B）随 ←/→ 或缩略条切换，只落在其他图片上；Esc 先结束对比再关闭查看器；手机上上下排列。
- 验收：浏览器旅程从资源库连续播放（下一条、上一条、默认不连播、打开连播后自动接下一条），查看器缩略条跳转与并排对比。

### S4 手机密度（已完成，`yeisme-control-center-mobile-density-v1`）

- 只在手机宽度（<640px）生效，桌面布局不变。
- `PageToolbar`：说明、来源卡片、观察时间和标了 `foldMetrics` 的计数条收成一行状态条（显示观察时间，“说明与来源”展开）；任务中心的视图切换这类导航仍直接显示，页面操作放在同一行。
- `NoticeStack`：第一条实际渲染出来的提示原地折成一行（截断，内部操作先收起），右侧“展开”看完整提示和操作；不复制提示文字，读屏和按文字查找都只有一份；资源库的过期提示也改走 `NoticeStack`。
- `FilterBar`：只留搜索框和“筛选 · n”，条件进全屏抽屉，写入的 URL 参数与桌面相同；资源库的来源、项目、结果、任务、权限和日期同样进抽屉，类型切换与搜索留在页面上。
- 请求记录：全范围汇总收成一行可展开；来源覆盖只列不完整的来源，其余合成一句计数；时间窗与来源下拉同一行。
- 实测第一条结果的 y：任务 579→345、资源 645→320、请求 765→369、提醒 505→337。
- 验收：浏览器旅程在 390×844 下检查四个列表首条 y<400，并检查状态条展开与筛选抽屉写参数。

### S5 状态提示收敛（已完成，`yeisme-control-center-status-notices-v1`）

- 来源状态只有一个来源 `src/shared/source-status.ts`：按连接状态逐个判断（与任务中心连接条、“服务与连接”页同一口径），分成部分连接读不到（列表可能不完整）、整次读取失败（数据可能已过期）、全部不可读（交给页面空状态）、没有任务连接。
- 顶栏来源状态在手机上也显示；弹层列出每个连接的中文原因，过期时写明显示的是哪一刻的结果，“查看服务与连接”跳转后弹层关闭（原来不关，手机上会挡住页面）。
- 页面最多一行：任务中心、资源库、审阅与交付、项目结果共用 `SourceStatusLine`，例如“2 个连接暂不可读，任务列表可能不完整：Scaena · 片场委托、Eikona · 旧项目（未授权）”，行尾“服务与连接”（可重读时还有“重新读取”）。首页的工作队列已列出读不到的来源，“可读连接”卡片一下就到“服务与连接”，所以只在数据可能过期时才加这一行。
- `NoticeStack` 在所有宽度都只占一行：第一条提示截断，提示自带的操作（`actions`）留在行尾，“展开 / 另有 n 条”在同一行，只在截断或还有其他提示时出现。
- 读取失败：两条任务通道都在传输中失败时保留上一批并标为“数据可能已过期”（原来会清空列表）；被拒绝时照常清空。读取失败的结果不再写入缓存，原来要等 30 秒，“重新读取”才真的重读。
- 顺带修复：Radix 弹层补上无障碍名称（来源状态、通知、筛选、审阅页“四种事实”）；只能横向滚动的表格在手机上可以用键盘聚焦。
- 验收：降级 fixture 下 11 个页面在 1440 与 390 宽度提示区不超过一行、同一原因最多一处；任务中心、资源库、审阅页一步到“服务与连接”；拦截任务读取后列表保留并标为可能过期，“重新读取”立即恢复。

### R1 历史记录一致（已完成，`yeisme-control-center-history-contract-v1`）

- 共用 `src/app/overlay-history.ts`：页面声明哪些参数是浮层（任务的 `task`/`preview`、资源的 `result`/`preview`、请求的 `request`、目录的 `entry`、剧集的 `episode`、首页的 `work_item`），写地址时按“打开 / 切换 / 关闭”处理历史：打开新增一条，所以后退关闭最上层且留在页面；开着时切换条目只替换；关闭时退回打开前那一条，所以下一次后退回到进入页面之前的地方。直接打开带详情的链接时，关闭只替换当前记录。
- 关闭判断读浏览器当前的地址与历史记录：React Router 的导航是过渡更新，界面上已经打开的查看器可能还拿着打开前的地址。打开位置存在按历史记录 key（每条唯一）对应的内存表里，刷新后忘记，关闭退化为替换。
- 查看器关闭时立即置为关闭（与打开对称）：原来只等地址变化，若打开时的地址还没提交，关闭的地址就不算变化，查看器会一直开着（嵌套场景在新的退回方式下必现，旧方式下是时序隐患）。浏览器后退同理，所以把预览放在地址里的页面（任务中心、资源库、项目）让查看器监听 popstate，地址里没有预览就立即关闭；打开后立刻后退或 Esc，三个入口各 5 次全部关闭。
- 首页工作项里的跳转链接不再先关闭工作项，所以从目标页后退会回到开着的工作项。
- 验收：浏览器旅程对 7 个详情与浮层检查“开着时后退关闭且留在页面”“Esc 关闭后一次后退回到首页”，以及“任务详情里打开查看器 → Esc → Esc → 后退回首页”；资源库原有的逐层后退检查保持通过。

### R2 宽屏行布局（已完成，`yeisme-control-center-wide-rows-v1`）

- 测量方法：每张表“主列文字结尾到下一列内容”的距离，屏宽 1440 / 1536 / 1920 / 2560。主列指给一行命名的那列。原来主列会占走其他列用不完的宽度：任务表设了 `w-full`，其余表按内容宽度分配，内容较长的主列分到最多。
- 表格单元格只认固定宽度，不认单独的最大宽度：单设 `max-width` 不会让列停止变宽，只能防止长文字把表撑宽。所以主列规则是“到某个表宽后固定为 560px”，在那之前用 `max-w-[560px]` 防止撑宽。
  - `mainColumn`：从 1200px 宽的表起固定。用于目录 MCP 工具、动作、资源紧凑列表。这些主列在 1200 时已经想要 560px 左右。
  - `narrowMainColumn`：从 1800px 起固定。用于模型、渠道、服务、资源详情列表。若从 1200 起固定，这些主列在 1536–1600 屏宽下会比原来宽，标题后最多多出 180px 空白；资源详情列表的其余六列还会被压到最小宽度。
  - `fillMainColumn`：表格窄于 1200 时占满剩余宽度，之后固定。用于任务中心与项目内三张表。
- 结果：
  - 1440 不变。
  - 1920 下标题到下一列的最大距离：任务 840→307，MCP 工具约 720→481，动作最大 713→454，资源紧凑列表 611→402。模型、渠道、服务、资源详情列表不变（模型 490，其余低于 450）。
  - 2560 下全部不超过 481（MCP 工具：名称和描述都短，主列 560px）。
  - 从 1536 起，模型与工具页上下叠放的六张表主列都是 560px，后面的列对齐。
- 长描述：工具表原来会因为一条长 owner 描述撑到约 2816px 并横向滚动，现在 1280–1920 下都不再超出容器。
- 资源列表：音频、视频的种类徽标放进与缩略图同尺寸的位置。紧凑列表与详情列表里，名称起点与行高各只有一种（原来名称起点相差 12px / 20px，详情列表行高在 66–85px 之间）。
- 团队成员表的主列文字已自带 220px 上限，不会撑宽表格；fixture 里没有成员数据可测，所以不改。
- 验收：浏览器旅程新增一项，在 1920 下检查任务表与工具表主列为 560px 且各表对齐；注入长描述后表格不横向滚动；资源紧凑列表的名称起点和行高各只有一种。

### R4 切页速度（已完成，`yeisme-control-center-page-switch-v1`）

- 测法：生产构建（`dist`）与 fixture API 同源提供（与发布服务器同样形态），在页面内计时：点击侧栏 → 目标页渲染且没有可见骨架，按动画帧取样。首次与再次各一遍，并加 4 倍 CPU 降速；开发服务器用同一方法对照。
- 发现：
  - 生产构建首次切页中位数 332ms，几乎每页都在 310–350ms，与页面复杂度无关。
  - 再次切页中位数只有 32ms。
  - 原因：路由页面是 `React.lazy`，Suspense 边界按页面重新挂载。空闲预取已把代码放进内存，lazy 组件第一次渲染仍会挂起；React 先显示骨架，再至少等 300ms 才显示页面。
- 修法：`src/app/route-page.tsx` 的 `routePage`，页面代码在内存里时直接渲染，只有代码还没加载完时才经过 lazy 组件和骨架。
  - 每次挂载只选一次：同一页中途从 lazy 换成已加载组件，会被重新挂载。
  - 空闲预取改为调用 `preload()`。
- 结果（生产构建，fixture rich，1440，两次复测一致）：

### R5 嵌套查看器的焦点回位（已完成，`yeisme-control-center-nested-focus-v1`）

- 复现：从任务详情里打开查看器，再用 Esc、关闭按钮或浏览器后退关闭，三种方式焦点都落到 body。查看器还开着时，打开它的按钮就已经不在页面里了。从任务行打开的对照正常。
- 原因：申请预览句柄期间，`ResultViewer` 把预览按钮设为 disabled。`Button` 会给带说明（`title`）的 disabled 按钮套上提示用的可聚焦外壳，元素结构变了，React 就重新挂载按钮。查看器记下的打开者脱离了页面，关闭时无处归还焦点。下载按钮也一样：按 Enter 下载后焦点会丢。
- 修法：
  - 预览、下载按钮只在动作确实不可用时 disabled。请求进行中保持可用，显示加载图标，设 `aria-busy`，并忽略重复点击。
  - `Button` 的 `disabledReason` 注释写明这条坑。全仓只有 `ResultViewer` 的三个按钮这样用。
- 结果：三种关闭方式都把焦点还给详情里的预览按钮。资源详情的“查看大图”打开、关闭后焦点也回到原按钮。任务详情的“下载”在下载期间保持焦点。
- 验收：浏览器旅程的嵌套场景（任务详情 → 查看器 → Esc）断言焦点回到详情里的预览按钮。

### R6 页面代码加载失败后自动恢复（已完成，`yeisme-control-center-chunk-recovery-v1`）

- 来源：R2、R4、R5 验证时，共享项目旅程三次在首页报“页面加载失败”，重跑即过。复现时抓到首页代码请求遇到 `ERR_NETWORK_CHANGED`（宿主网络抖动）。
- 应用的问题：浏览器在文档存续期间会记住失败的模块请求，再次导入同一地址不会重新请求，只会再次失败。
  - 实测：让空闲预取取用量页代码时失败一次，再切到用量页，开发服务器和生产构建都没有重新请求，停在错误页。
  - 登录后的空闲预取会一次取全部页面代码，所以那一刻的网络抖动会让所有没取到的页面在这次打开期间都进不去，只能手动重新加载。原来的“重新加载”按钮正是唯一出路。
- 修法：`PageBoundary` 遇到页面代码加载失败、浏览器在线、且一分钟内没有自动重新加载过时，保持页面骨架并自动重新加载一次（地址不变）。
  - 离线、一分钟内再次失败、或者会话存储不可用时，仍显示错误页和按钮。
  - 判断逻辑在 `src/app/chunk-recovery.ts`，有单元测试。
- 代价：自动重新加载会中断音频播放器，并清空 R1 的打开位置表（关闭浮层退化为替换）。只在页面代码加载失败时发生。
- 结果：
  - 失败一次：自动恢复，代码请求 2 次。
  - 一直失败：只重新加载一次就停在错误页，没有循环。
  - 开发服务器与生产构建结果相同。
- 验收：浏览器旅程新增一项，用独立页面覆盖这两种情形。

### T1 处理过的提醒不再复现（已完成，`yeisme-control-center-reminder-identity-v1`）

#### 批次服务端分页与详情（A1，2026-10-30，已发布）

变更 `yeisme-control-center-completion-v1` 2.1–2.3、3.1，设计见 [前端接口补齐](frontend-api-completion.md) A1。

- 项目批次一次只取一页（默认 20），最新的在前。
  - 名称或 id 搜索、状态、工具、日期都放在地址里，刷新后恢复；改筛选会回到第一页。
  - “更早的批次”用签名游标，15 分钟有效，换人、换权限或换筛选都不能复用。
  - 游标失效时（例如共享设置改了）自动回到最新一页并提示，而不是报错。
- 提醒和链接里的 `?batch=` 直接打开那一个批次，不要求它在第一页；从别的范围打开时先切换到该共享项目。
- 服务器只观察当前页和打开的批次：每次最多读 24 个进行中的生成项，同时 4 个，最久未读的优先。读不到的来源会在页上说明，显示的是上次保存的状态。
- 完成提醒只在观察到状态变化时发一次。翻回旧批次不会给成员补发多年前的“已完成”（原来每次列表都会为全部历史批次补发）。
- 过滤、排序、计数都在 SQL 里完成，加了索引（迁移 0011）。4,000 个批次的项目，一页从 107 ms 降到 1.7 ms。
- 成果页的按批次筛选只取最新 20 个批次，链接指向更早的批次时再单独读取。
- 测试用 fake Eikona 补上批次合同（输入、计划、提交、对账、成员），不触达 Provider。
